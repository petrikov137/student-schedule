لماذا نحتاج Properties؟

المشكلة والحل

قبل أن نعرف ما هي الـ Property، لازم نفهم المشكلة اللي جاءت تحلها.

المشكلة: الـ private field

في OOP، الـ Encapsulation يقول: البيانات داخل الكلاس يجب أن تكون private — أي لا يمكن لأحد خارج الكلاس الوصول إليها مباشرة. لكن هذا يخلق مشكلة:

❌ المشكلة 
class Student
{
    private int age; // private = لا يُرى من الخارج
}

// في كلاس آخر:
Student s = new Student();
s.age = 20; // ❌ خطأ! لا يمكن الوصول
🚫
النتيجة: إذا جعلنا كل شيء private، لا يمكن لأحد قراءة أو تغيير البيانات. وإذا جعلناها public، كسرنا قاعدة الـ Encapsulation وفقدنا التحكم.

الحل: Properties! ✅

الـ Property هي بوابة آمنة ومتحكم بها للوصول إلى الـ private fields. هي تجمع بين:

🔒 الحماية

البيانات تبقى private داخل الكلاس

🚪 الوصول

نسمح بالقراءة والكتابة بشكل منظم

✅ التحقق

نستطيع التحقق من القيمة قبل حفظها

🧹 النظافة

كود أنظف من استخدام دوال get/set منفصلة

📖

ما هي الـ Property؟

التعريف والبنية
💡
التعريف: الـ Property هي عضو في الكلاس يوفر طريقة مرنة للقراءة والكتابة على حقل private. تعمل من الخارج كأنها متغير عادي، لكن من الداخل هي في الحقيقة دالتان مخفيتان.

البنية الأساسية (Syntax)

C# — البنية 
access_modifier  data_type  PropertyName
{
    get
    {
        return fieldName; // إرجاع قيمة الحقل
    }
    set
    {
        fieldName = value; // value = القيمة اللي أرسلها المستخدم
    }
}

أنواع الـ Properties

Read / Write / Both
👁️

Read-Only

تحتوي على get فقط
يمكن القراءة لكن لا يمكن التغيير من الخارج

✏️

Write-Only

تحتوي على set فقط
يمكن الكتابة لكن لا يمكن القراءة من الخارج

🔄

Read-Write

تحتوي على get و set معاً
الأكثر شيوعاً — قراءة وكتابة

مثال: Read-Only Property

C# — Read Only 
class Circle
{
    private double radius = 5.0;

    public double Radius
    {
        get { return radius; }
        // لا يوجد set — لا يمكن تغيير القيمة من الخارج
    }
}

Circle c = new Circle();
Console.WriteLine(c.Radius); // ✅ يعمل
c.Radius = 10;               // ❌ خطأ! لا يوجد set

مثال: Read-Write مع Validation ⭐ (متقدم مهم)

C# — Validation في set 
class Student
{
    private int age;

    public int Age
    {
        get { return age; }
        set
        {
            // نتحقق من القيمة قبل حفظها!
            if (value >= 0 && value <= 150)
                age = value;
            else
                Console.WriteLine("عمر غير صالح!");
        }
    }
}

Student s = new Student();
s.Age = 20;   // ✅ يعمل
s.Age = -5;   // ✅ لا يحفظ + يظهر رسالة
⭐
هذا هو أهم فائدة للـ Properties! نستطيع إضافة منطق (logic) في الـ set لنتحقق من البيانات قبل حفظها. هذا مستحيل لو كان الحقل public مباشرة.

مثال كامل — كلاس Car

من المحاضرة العملية

هذا هو المثال الكامل من المحاضرة مع شرح كل سطر:

C# — Car Class 
using System;

class Car
{
    // ① الحقول الخاصة — لا يراها أحد من الخارج
    private string model;
    private int    year;

    // ② Property للـ model — تسمح بالقراءة والكتابة
    public string Model
    {
        get { return model; }
        set { model = value; }
    }

    // ③ Property للـ year
    public int Year
    {
        get { return year; }
        set { year = value; }
    }

    // ④ دالة لعرض المعلومات
    public void DisplayCarInfo()
    {
        Console.WriteLine("Car Model: " + model);
        Console.WriteLine("Car Year: "  + year);
    }
}

class Program
{
    static void Main()
    {
        // ⑤ إنشاء كائن من الكلاس
        Car c = new Car();

        // ⑥ استخدام الـ Properties
        c.Model = "Toyota"; // يستدعي set في Model
        c.Year  = 2025;    // يستدعي set في Year

        // ⑦ عرض النتيجة
        c.DisplayCarInfo();
        // Output: Car Model: Toyota
        //         Car Year: 2025
    }
}

شرح خطوة بخطوة

  1. الحقول private: model و year مخفيان تماماً — هذا هو الـ Encapsulation
  2. الـ Properties public: Model و Year هي البوابة الوحيدة للوصول
  3. عند الكتابة: c.Model = "Toyota" → يُستدعى set تلقائياً → يُحفظ في model
  4. عند القراءة: c.Model → يُستدعى get تلقائياً → يُرجع قيمة model

// بدون أي تحقق
c.model = ""; // ✅ "يعمل" لكن خطر

Auto-Implemented Properties

اختصار C# الحديث

C# يوفر طريقة مختصرة لكتابة Properties بسيطة — تسمى Auto-Implemented Properties. المترجم يُنشئ الحقل الخاص تلقائياً!

📝 الطريقة التقليدية

private string name;

public string Name
{
  get { return name; }
  set { name = value; }
}

⚡ Auto Property

// نفس النتيجة!
public string Name
  { get; set; }

// أقصر بكثير ✨
⚠️
متى لا تستخدم Auto Property؟ عندما تحتاج إضافة منطق أو تحقق (Validation) في الـ get أو set — في هذه الحالة استخدم الطريقة التقليدية.

مثال كامل بالطريقتين

C# — Auto Properties 
class Book
{
    // Auto Properties — مختصرة ونظيفة
    public string Title { get; set; }
    public double Price { get; set; }

    // Read-only auto property (C# 6+)
    public string ISBN { get; } = "978-3-16";

    public void DisplayBookInfo()
    {
        Console.WriteLine($"العنوان: {Title}, السعر: {Price}");
    }
}

Book b = new Book();
b.Title = "تعلم C#";
b.Price = 25.5;
b.DisplayBookInfo();

ملخص: متى تستخدم كل طريقة؟

⚡ Auto Property

عندما لا تحتاج منطق إضافي — فقط قراءة وكتابة بسيطة

📝 Traditional Property

عندما تحتاج Validation أو حسابات أو شروط

👁️ Read-Only

get فقط — للبيانات التي لا يجب تغييرها من الخارج

✏️ Write-Only

set فقط — نادر — مثل حقل كلمة المرور

Inheritance — الوراثة

المحاضرة الثالثة العملي
💡
التعريف: الوراثة تسمح لكلاس جديد (Derived Class) بأن يرث كل خصائص وسلوكيات كلاس موجود (Base Class)، مع إمكانية الإضافة والتعديل.

لماذا نستخدم الوراثة؟

♻️ إعادة استخدام الكود

تكتب الكود مرة واحدة في Base Class ويرثه كل الكلاسات الفرعية

🏗️ التنظيم الهرمي

تنظيم الكلاسات في هرم منطقي: Animal → Dog, Cat, Bird

➕ الإضافة والتخصيص

كل كلاس فرعي يضيف ما يخصه دون تكرار الكود المشترك

🔧 سهولة الصيانة

تعديل Base Class يؤثر على جميع الكلاسات الفرعية تلقائياً

الصيغة الأساسية

C# — بنية الوراثة 
// Base Class (الكلاس الأساسي / الأب)
class Person
{
    private string name;
    public string Name
    {
        get { return name; }
        set { name = value; }
    }
}

// Derived Class (الكلاس المشتق / الابن) — يرث من Person
class Student : Person   // علامة : تعني "يرث من"
{
    public void DisplayInfo()
    {
        // يصل لـ Name المورثة من Person
        Console.WriteLine("Student: " + Name);
    }
}

Polymorphism — تعدد الأشكال

المحاضرة الثانية + الرابعة
📖
Polymorphism = Poly (كثير) + Morph (شكل)
قدرة كائنات من أنواع مختلفة على الاستجابة لنفس الاستدعاء بطرق مختلفة — كل كائن يتصرف حسب طبيعته الخاصة تلقائياً أثناء التشغيل. هو أحد الركائز الأربعة لـ OOP.

🌍 تشبيه من الحياة

زر "شغّل" واحد — على التلفاز يُشغّل التلفاز، على الراديو يُشغّل الراديو، على السيارة يُشغّل السيارة. نفس الزر، سلوك مختلف حسب الجهاز — هذا تماماً هو Polymorphism.

🎯 المشكلة التي يحلّها

❌ بدون Polymorphism

كود متكرر — كل نوع جديد يتطلب تعديل الكود القديم:

if (a is Dog)    PrintDog(a);

else if (a is Bird)   PrintBird(a);
// كل نوع جديد = سطر if جديد!

foreach (Animal a in animals)

الكلمة virtual

تُضاف في Base Class

تُوضع virtual أمام الدالة في الـ Base Class لتقول: "هذه الدالة لها تنفيذ افتراضي، لكن يمكن لأي Derived Class إعادة تعريفها."

C# — virtual 
class Animal
{
    // virtual = قابلة للـ override في الفرعيات
    public virtual void MakeSound()
    {
        Console.WriteLine("Some animal sound...");
    }

    // دالة عادية = لا يمكن override لها
    public void Breathe()
    {
        Console.WriteLine("Breathing...");
    }
}
⚠️
virtual vs abstract: الـ virtual لها جسم (تنفيذ افتراضي) والـ override اختياري. أما abstract فلا جسم لها والـ override إجباري.
📌
يمكن أن يكون virtual: Methods ✅ — Properties ✅ — Events ✅ — Indexers ✅
لا يمكن أن يكون virtual: Fields ❌ — static methods ❌ — Constructors ❌
🟢

الكلمة override

تُضاف في Derived Class

تُستخدم override في الـ Derived Class لإعادة تعريف دالة virtual أو abstract بتنفيذ مخصص لهذا الكلاس.

C# — override في كلاسات مختلفة 
class Dog : Animal
{
    public override void MakeSound()
    { Console.WriteLine("Woof! Woof!"); }
}

class Cat : Animal
{
    public override void MakeSound()
    { Console.WriteLine("Meow!"); }
}

class Bird : Animal
{
    public override void MakeSound()
    { Console.WriteLine("Tweet! Tweet!"); }
}

class Program
{
    static void Main()
    {
        Animal[] animals = {
            new Dog(),
            new Cat(),
            new Bird()
        };
        foreach (Animal a in animals)
            a.MakeSound();
        // Woof! Woof!
        // Meow!
        // Tweet! Tweet!
    }
}
🎯
المتغيرات كلها من نوع Animal، لكن عند استدعاء MakeSound() يُنفَّذ الكود الخاص بالكائن الحقيقي (Dog أو Cat أو Bird) — هذا هو Runtime Polymorphism.

قواعد الـ override — احفظها جيداً

📝 نفس التوقيع تماماً

نفس الاسم + نفس المعاملات + نفس نوع الإرجاع

✅ يجب virtual/abstract/override

لا يمكن override لدالة عادية أو static

🚫 ممنوع مع: new, static, virtual, abstract

هذه المعدّلات لا تُستخدم مع override

⛓️ تبقى virtual للأبد

الدالة بعد override تبقى virtual في كل الكلاسات الفرعية اللاحقة

virtual تنتقل عبر سلسلة الوراثة

مفهوم مهم جداً

إذا أعاد كلاس تعريف دالة virtual، تبقى هذه الدالة virtual تلقائياً في كل الكلاسات المشتقة منه — بغض النظر عن عدد مستويات الوراثة.

C# — virtual chain A → B → C 
class A
{
    public virtual void DoWork()
    { Console.WriteLine("A"); }
}

class B : A
{
    public override void DoWork() // تبقى virtual تلقائياً
    { Console.WriteLine("B"); }
}

class C : B
{
    public override void DoWork() // يمكن override من B
    { Console.WriteLine("C"); }
}

class Program
{
    static void Main()
    {
        A obj = new C(); // مرجع A — كائن C
        obj.DoWork();    // C  ← آخر override في السلسلة
    }
}
💡
دائماً يُنفَّذ آخر override في سلسلة الوراثة — حتى لو استخدمت مرجعاً من نوع الكلاس الأعلى في السلسلة.
C# — مثال آخر: base1 → derived1 + derived2 
class base1
{
    public virtual void who()
    { Console.WriteLine("base"); }
}
class derived1 : base1
{
    public override void who()
    { Console.WriteLine("derived1"); }
}
class derived2 : base1
{
    public override void who()
    { Console.WriteLine("derived2"); }
}
class Program
{
    static void Main()
    {
        base1 bref;

        bref = new base1();
        bref.who();    // base

        bref = new derived1();
        bref.who();    // derived1

        bref = new derived2();
        bref.who();    // derived2
    }
}

الكلمة new — Method Hiding

إخفاء دالة الـ Base Class

عندما تريد في الـ Derived Class أن تُعرِّف دالة بنفس اسم دالة موجودة في الـ Base Class، تستخدم الكلمة new لإخفاء الدالة الأصلية — وهذا يختلف جوهرياً عن override.

C# — new keyword (Method Hiding) 
class Car
{
    public void ShowType()
    {
        Console.WriteLine("This is a regular car.");
    }
}

class ElectricCar : Car
{
    // new = يُخفي ShowType() الموروثة ويستبدلها
    public new void ShowType()
    {
        Console.WriteLine("This is an electric car.");
    }
}

class Program
{
    static void Main()
    {
        ElectricCar e = new ElectricCar();
        e.ShowType();           // This is an electric car.

        Car c = (Car)e;          // تحويل (casting) للـ Base
        c.ShowType();           // This is a regular car. ← دالة الأب!
    }
}

⚡ الفرق الجوهري: override مقابل new

الخاصية override new (hiding)
تحتاج virtual في Base؟ ✅ نعم إجباري ❌ لا — أي دالة
عند استخدام Base reference يُنفَّذ الـ Derived يُنفَّذ الـ Base
نوع الـ Polymorphism Runtime (حقيقي) Compile-time (ظاهري)
الاستخدام الأنسب تغيير السلوك فعلياً نسخة موازية مختلفة
C# — الفرق واضح بمثال 
class A
{
    public virtual void Test()
    { Console.WriteLine("A-virtual"); }
}
class B_Override : A
{
    public override void Test()
    { Console.WriteLine("B-override"); }
}
class B_New : A
{
    public new void Test()
    { Console.WriteLine("B-new"); }
}

class Program
{
    static void Main()
    {
        A x = new B_Override();
        x.Test(); // B-override  ← يُنفَّذ Derived (Polymorphism)

        A y = new B_New();
        y.Test(); // A-virtual   ← يُنفَّذ Base! (ليس Polymorphism)
    }
}
🚨
الخلاصة الذهبية: استخدم override عندما تريد Polymorphism حقيقياً. استخدم new فقط عندما تريد إنشاء دالة مستقلة تماماً في الـ Derived Class لا تُبطل الأصلية.

بنية الـ Abstract Class

الصيغة + القواعد
C# — بنية abstract class 
// الكلمة abstract قبل class
abstract class Shape
{
    // ① حقول عادية — مسموح
    public double Width;
    public double Height;

    // ② دالة مجردة — بلا جسم {} — يجب override في الفرعيات
    public abstract double CalculateArea();

    // ③ دالة عادية — لها جسم — تُستخدم مباشرةً
    public void Display()
    {
        Console.WriteLine("This is a shape");
    }

    // ④ دالة virtual — لها جسم — override اختياري
    public virtual void Describe()
    {
        Console.WriteLine("Width=" + Width + " Height=" + Height);
    }
}
⚠️
قاعدة مهمة: إذا كان أي عضو في الكلاس من نوع abstract — يجب أن يكون الكلاس نفسه abstract أيضاً. لكن يمكن للـ abstract class أن يحتوي دوالاً غير مجردة (عادية أو virtual).

القوة الحقيقية

الـ Abstract Class يتكامل مع Polymorphism بشكل رائع — تُعرِّف كلاس مجرد كـ base، وتستخدم مرجعه لتشغيل أي كلاس فرعي:

C# — Abstract + Polymorphism 
abstract class C1
{
    abstract public void print();

    public void print2()
    {
        Console.WriteLine("called from class C1");
    }
}

class C2 : C1
{
    public override void print()
    {
        Console.WriteLine("Test Abstract");
    }
}

class Program
{
    static void Main()
    {
        // C1 ob1 = new C1(); ❌ خطأ!

        C2 ob = new C2();
        ob.print();   // Test Abstract
        ob.print2();  // called from class C1
    }
}

ما هو الـ Interface؟

📘
التعريف: الـ Interface هو عقد (Contract) يحدد مجموعة من الدوال (methods) التي يجب على أي كلاس ينفّذه أن يوفّرها. لكنه لا يحتوي على أي تنفيذ — فقط الإعلانات (declarations).

🔑 الفكرة الأساسية

تخيّل أن الـ Interface هو قائمة متطلبات أو "وصف وظيفة". إذا وافقت على الوظيفة (نفّذت الـ Interface)، يجب أن توفر كل ما هو مطلوب فيها.

📜 فقط توقيعات

يحتوي على إعلانات الدوال فقط — بدون كود تنفيذي داخله

🚫 لا instances

لا يمكن إنشاء كائن مباشر من الـ Interface: new IShape() ❌

🔓 Public تلقائياً

جميع أعضاء الـ Interface هم public بالافتراض — لا حاجة لكتابة public

🏷️ حرف I

بالاتفاقية يبدأ اسم الـ Interface بحرف I الكبير: IShape, IAnimal

✍️

صيغة الـ Interface (Syntax)

C# — Interface Syntax 
// تعريف الـ Interface بكلمة interface
interface ISpaceship
{
    // توقيعات دوال فقط — بدون تنفيذ
    void LaserHit();
    void Move(int x, int y);
    int  GetSpeed();

    // ❌ لا يوجد: حقول بيانات (fields)
    // ❌ لا يوجد: كود تنفيذ (body)
}

Interface مقابل Abstract Class

الخاصية 🔌 Interface 🏛️ Abstract Class
البيانات (Fields)❌ لا يحتوي✅ يحتوي
تنفيذ الدوال❌ لا يوجد✅ يوجد (غير abstract)
الدوال الافتراضية❌ ليست virtual تلقائياً✅ abstract = virtual
صلاحية الوصولدائماً publicيمكن protected
الوراثة المتعددة✅ يدعم (class C : IA, IB)❌ واحدة فقط
Constructor❌ لا يحتوي✅ يحتوي
الكائنات (Instances)❌ لا يمكن إنشاؤها❌ لا يمكن إنشاؤها

متى تستخدم Interface ومتى تستخدم Abstract Class؟

🔌
استخدم Interface عندما: تريد تعريف سلوك مشترك بين كلاسات لا علاقة بينها، أو تحتاج للوراثة المتعددة، أو تريد تعريف "عقد" بدون تفاصيل تنفيذ.
🏛️
استخدم Abstract Class عندما: تريد مشاركة كود مشترك بين الكلاسات المشتقة، أو تحتاج لتخزين بيانات مشتركة (fields)، أو الكلاسات تمثل "نفس العائلة".

الدوال الافتراضية داخل الـ Interface

⚠️
نقطة مهمة جداً: دوال الـ Interface ليست virtual تلقائياً — بعكس دوال الـ Abstract Class. إذا أردت الـ override الحقيقي يجب أن تجعلها virtual في الكلاس الذي يُنفّذها.

المثال: بدون virtual — سلوك غير متوقع

C# — بدون virtual 
interface ISpaceship { void LaserHit(); }

class CombatShip : ISpaceship
{
    // دالة عادية — ليست virtual
    public void LaserHit() { Console.WriteLine("CombatShip fires!"); }
}

class AdvancedCombatShip : CombatShip
{
    // new = إخفاء (Hiding) وليس Override حقيقي
    public new void LaserHit() { Console.WriteLine("Advanced fires!"); }
}

ISpaceship s = new CombatShip();
s.LaserHit();       // ✅ CombatShip fires!

s = new AdvancedCombatShip();
s.LaserHit();       // ⚠️ CombatShip fires! ← ليس Advanced!
// السبب: Interface لا يرى new — لذا يستدعي CombatShip

الحل: استخدام virtual + override

C# — مع virtual + override 
class CombatShip : ISpaceship
{
    virtual public void LaserHit() { Console.WriteLine("CombatShip fires!"); }
}

class AdvancedCombatShip : CombatShip
{
    override public void LaserHit() { Console.WriteLine("Advanced fires!"); }
}

ISpaceship s = new CombatShip();
s.LaserHit();       // ✅ CombatShip fires!

s = new AdvancedCombatShip();
s.LaserHit();       // ✅ Advanced fires! ← صحيح الآن

الفرق: عندما تستخدم virtual في CombatShip وoverride في AdvancedCombatShip، يعمل الـ Polymorphism بشكل صحيح حتى عبر متغير من نوع الـ Interface.

الـ Properties داخل الـ Interface

يمكن تضمين Properties داخل الـ Interface — لكن بدون تنفيذ (فقط get; وset;):

C# — Properties in Interface 
public interface IShape
{
    // Property في الـ Interface — بدون تنفيذ
    int Sides
    {
        get;
        set;
    }
    double Area();
}

public class Square : IShape
{
    private int InSides;
    public int SideLength;

    // تنفيذ الـ Property من الـ Interface
    public int Sides
    {
        get { return InSides; }
        set { InSides = value; }
    }

    public double Area()
    {
        return SideLength * SideLength;
    }

    public Square() { Sides = 4; } // يضبط Sides=4 في الـ constructor
}

class Program
{
    static void Main()
    {
        Square sq = new Square();
        sq.SideLength = 5;
        Console.WriteLine("Area: "  + sq.Area());   // 25
        Console.WriteLine("Sides: " + sq.Sides);   // 4
    }
}

١

ما هو الـ Interface؟

🔍
السؤال: ما الفرق بين الـ Interface والـ Abstract Class من حيث الغرض؟
✅
الجواب:
الـ Interface هو عقد بحت يحدد ماذا يجب أن يفعل الكلاس — جميع أعضائه abstract تلقائياً ولا يوجد فيه أي تنفيذ.

الـ Abstract Class يحدد ما هو الشيء — يمكنه أن يحتوي أعضاء منفّذة وأعضاء مجردة، ويملك fields وconstructor.

قاعدة ذهبية: استخدم Interface عندما تريد عقداً بين كلاسات غير مترابطة. استخدم Abstract Class عندما تكون الكلاسات في نفس العائلة.
٢

لماذا لا يمكن إضافة fields للـ Interface؟

🔍
السؤال: لماذا لا يسمح C# بإضافة fields (حقول بيانات) داخل الـ Interface؟
✅
الجواب:
الـ Interface يُعرّف السلوك فقط — أي ماذا يستطيع الكلاس أن يفعل، وليس ما يخزّنه. إضافة fields تعني تخزين بيانات وهذا ينتمي للكلاسات وليس للعقود.

إذا احتجت بيانات مشتركة بين كلاسات، استخدم abstract class بدلاً من الـ Interface.
٣

الوراثة المتعددة عبر Interfaces

🔍
السؤال: كيف يحل الـ Interface مشكلة عدم دعم C# للوراثة المتعددة بين الكلاسات؟
✅
الجواب:
في C# لا يمكن لكلاس أن يرث من أكثر من كلاس واحد مباشرة. لكن يمكن لكلاس واحد أن يُنفّذ أكثر من Interface في نفس الوقت:

class MultiFunctionDevice : IPrinter, IScanner { }

هذا يمنح الكلاس قدرات من مصادر متعددة دون مشاكل الوراثة المتعددة.
٤

ماذا يحدث إذا لم يُنفّذ الكلاس عضواً في الـ Interface؟

🔍
السؤال: إذا عرّف الـ Interface دالتَين وأنت نفّذت دالة واحدة فقط في الكلاس — ماذا يحدث؟
🚫
الجواب:
خطأ في وقت الترجمة (Compile-time Error) — المترجم يرفض الكود ولا يُشغّله. الـ Interface عقد ملزم: إما تُنفّذ جميع أعضائه أو تجعل الكلاس نفسه abstract.

الرسالة المعتادة: does not implement interface member
٥

استخدام متغير من نوع Interface (Interface Reference)

🔍
السؤال: ما فائدة كتابة IPayment payment = new CreditCardPayment(); بدلاً من CreditCardPayment payment = new CreditCardPayment();؟
✅
الجواب:
استخدام متغير من نوع الـ Interface يحقق Polymorphism — نفس المتغير يستطيع أن يشير لأي كلاس يُنفّذ الـ Interface:

payment = new CreditCardPayment();  // يعمل
payment = new CashPayment();       // يعمل أيضاً!
هذا يجعل الكود مرناً وقابلاً للتوسع — يمكن إضافة طرق دفع جديدة مستقبلاً دون تغيير الكود الحالي.
٦

هل يمكن إنشاء كائن مباشرة من الـ Interface؟

🔍
السؤال: هل هذا الكود صحيح؟ IPayment p = new IPayment();
🚫
الجواب: لا — خطأ!
لا يمكن إنشاء كائن مباشرة من Interface لأنه لا يحتوي أي تنفيذ — هو مجرد عقد. يجب دائماً إنشاء كائن من كلاس يُنفّذ الـ Interface:

❌ IPayment p = new IPayment();
✅ IPayment p = new CreditCardPayment();
٧

لماذا تبدأ أسماء الـ Interfaces بحرف I؟

✅
الجواب:
هذه اتفاقية تسمية (Naming Convention) معتمدة في C# — الحرف I يرمز لـ Interface. المترجم لا يُجبرك عليها لكن:
• تجعل الكود أوضح للقراءة
• تميّز الـ Interface فوراً عن الكلاس العادي
• معيار الصناعة في .NET

أمثلة: IPrinter, IScanner, IPayment, IDisposable, IEnumerable

using System;

interface ILibraryItem
{
    string GetTitle();
    void   Borrow();
    void   Return();
}

abstract class LibraryItem : ILibraryItem
{
    protected string title;
    protected bool isBorrowed = false;

    public LibraryItem(string t) { title = t; }

    public string GetTitle() => title;
    public abstract string GetType();

    {
        if (!isBorrowed) { isBorrowed = true; Console.WriteLine($"📖 Borrowed: {title}"); }
        else Console.WriteLine($"❌ Already borrowed: {title}");
    }
    public void Return()
    {
        isBorrowed = false;
        Console.WriteLine($"✅ Returned: {title}");
    }
}

{
    public Book(string t) : base(t) { }
    public override string GetType() => "📚 Book";
}

{
    public DVD(string t) : base(t) { }
    public override string GetType() => "💿 DVD";
}

{
    static void Main()
    {
        ILibraryItem[] items = {
            new Book("C# Programming"),
            new DVD("OOP Tutorial"),
            new Book("Design Patterns")
        };

        foreach (var item in items)
        {
            Console.WriteLine($"Title: {item.GetTitle()}");
            item.Borrow();
            item.Borrow(); // محاولة ثانية
            item.Return();
            Console.WriteLine();
        }
    }
}

Method Overloading — تحميل زائد للدوال

📘
التعريف: Method Overloading يعني تعريف أكثر من دالة بنفس الاسم داخل نفس الكلاس، لكن بـ signature مختلفة لكل واحدة منها.

🔑 ما هو الـ Signature؟

الـ Signature هو اسم الدالة + قائمة المعاملات (parameters). يجب أن تختلف الدوال المحمّلة (overloaded) في:

✅
عدد المعاملات — مثلاً: Add(int a) وAdd(int a, int b)
✅
نوع المعاملات — مثلاً: Print(int x) وPrint(double x)
❌
نوع القيمة المُرجَعة وحده لا يكفي للتمييز — يُسبب خطأ ترجمة

مثال — Constructor Overloading

C# — Method + Constructor Overloading 
using System;

class Box
{
    public double Width, Height, Depth;

    // Constructor Overloading — ثلاثة constructors بنفس الاسم
    public Box() { Width = Height = Depth = 0; }           // بدون معاملات
    public Box(double side) { Width = Height = Depth = side; }  // مكعب
    public Box(double w, double h, double d)                   // أبعاد مختلفة
    { Width = w; Height = h; Depth = d; }

    // Method Overloading — نفس الاسم Volume بمعاملات مختلفة
    public double Volume() => Width * Height * Depth;
    public double Volume(double scale) => Width * Height * Depth * scale;
}

class Program
{
    static void Main()
    {
        Box b1 = new Box();          // constructor بلا معاملات
        Box b2 = new Box(5.0);       // constructor مكعب
        Box b3 = new Box(3, 4, 5);   // constructor أبعاد مختلفة

        Console.WriteLine($"b2 Volume: {b2.Volume()}");          // 125
        Console.WriteLine($"b3 Volume×2: {b3.Volume(2)}");       // 120
    }
}

ما هو الـ Operator؟ أنواعه

الـ Operator هو رمز يأخذ واحداً أو أكثر من المعاملات (operands) ويُرجع قيمة.

Unary Operators (أحادي)

يأخذ معامل واحد فقط

++   --   -   +   !   ~

مثال: ++x ، -y

Binary Operators (ثنائي)

يأخذ معاملَين

+  -  *  /  %  >  <  ==  !=

مثال: a + b ، x == y

Ternary Operator (ثلاثي)

يأخذ ثلاثة معاملات — الوحيد في C#

condition ? val1 : val2

مثال: x > 0 ? "pos" : "neg"

Associativity — الترابطية

🔄
عندما يكون لعمليتَين نفس الأولوية (precedence)، يتم التقييم بناءً على الترابطية:
Left-associative: من اليسار لليمين — مثال: x * y / z = (x*y)/z
Right-associative: من اليمين لليسار — مثال: عمليات الإسناد a = b = 5

Operator Overloading — التحميل الزائد للمعاملات

💡
التعريف: في C#، يمكن تغيير سلوك (behavior) المعاملات الحسابية مع الكلاسات المُعرَّفة من قِبل المستخدم. هذه العملية تُسمى Operator Overloading. أي: نُعلّم البرنامج كيف يُجري العمليات على الكائنات (objects).

الصيغة العامة (General Syntax)

C# — Operator Overloading Syntax 
public static return_type operator op (Type t1 [, Type t2])
{
    // الكود هنا
}
المصطلحالمعنى
public staticإلزامي — كل operator يجب أن يكون public وstatic
return_typeنوع النتيجة — لا يمكن void
للـ true/false → bool
للـ ++ و-- → نفس نوع الكلاس
operator opالكلمة المحجوزة operator متبوعة برمز العملية (+، -، *، ==، ...)
Type t1المعامل الأول — يجب أن يكون على الأقل واحد من نوع الكلاس نفسه
Type t2المعامل الثاني (للـ binary operators فقط)
📋

قواعد Operator Overloading

١
public static Point operator +(Point a, Point b)

يجب أن يكون الـ operator public وstatic دائماً — لا يمكن private أو protected.

٢
// ❌ operator virtual/abstract/override/sealed → خطأ

لا يمكن استخدام المُعدِّلات virtual أو abstract أو override أو sealed مع الـ operators.

٣
// * هو binary → يجب أن يبقى binary public static Point operator *(Point a, int scale)

لا يمكن تغيير عدد المعاملات — الـ unary يبقى unary والـ binary يبقى binary.

٤
// ❌ لا يمكن اختراع رمز جديد مثل ** أو @@

لا يمكن اختراع رموز عمليات جديدة — فقط الرموز الموجودة في C# يمكن تحميلها.

٥
// إذا overloaded == يجب overload != // إذا overloaded < يجب overload > // إذا overloaded true يجب overload false

Comparison operators يجب تحميلها أزواجاً: == مع !=، و< مع >، و<= مع >=، وtrue مع false.

٦
// لا يمكن overload: = . ?: -> && || new sizeof typeof

بعض الرموز لا يمكن تحميلها نهائياً: مشغل الإسناد =، ومشغل الوصول .، والـ ternary ?:، وغيرها.

📊

جدول المعاملات القابلة للتحميل

النوعالرموزملاحظة
Unary+ - ! ~ ++ -- true falseيأخذ معاملاً واحداً
Binary+ - * / % & | ^ << >>يأخذ معاملَين
Comparison== != < > <= >=يجب تحميلها أزواجاً
غير قابلة= . ?: -> && || new sizeof typeofلا يمكن تحميلها

مثال ١ — تحميل الـ Unary: المنفي (-) والزيادة (++)

C# — Unary Operator Overloading 
using System;

class Point
{
    public int X, Y;

    // تحميل المعامل الأحادي السالب -
    public static Point operator -(Point RValue)
    {
        Point NewPoint = new Point();
        NewPoint.X = -RValue.X;   // عكس الإشارة
        NewPoint.Y = -RValue.Y;
        return NewPoint;
    }

    // تحميل معامل الزيادة ++
    public static Point operator ++(Point RValue)
    {
        Point NewPoint = new Point();
        NewPoint.X = RValue.X + 1;   // زيادة 1
        NewPoint.Y = RValue.Y + 1;
        return NewPoint;
    }

    static void Main()
    {
        Point MyPoint = new Point();
        MyPoint.X = -100; MyPoint.Y = 200;

        Console.WriteLine($"Original : {MyPoint.X}, {MyPoint.Y}");  // -100, 200

        MyPoint = -MyPoint;
        Console.WriteLine($"After  - : {MyPoint.X}, {MyPoint.Y}");  // 100, -200

        MyPoint = ++MyPoint;
        Console.WriteLine($"After ++ : {MyPoint.X}, {MyPoint.Y}");  // 101, -199
    }
}

مثال ٢ — تحميل true و false

💡
عند تحميل true يجب حتماً تحميل false أيضاً. هذا يُتيح استخدام الكائن مباشرةً في شروط if.
C# — true / false Overloading 
using System;

class ThreeD
{
    int x, y, z;

    public ThreeD() { x = y = z = 0; }
    public ThreeD(int i, int j, int k) { x = i; y = j; z = k; }

    // true: إذا أي قيمة غير صفر → الكائن يُعتبر true
    public static bool operator true(ThreeD op)
    {
        return (op.x != 0) || (op.y != 0) || (op.z != 0);
    }

    // false: إذا جميع القيم صفر → الكائن يُعتبر false
    public static bool operator false(ThreeD op)
    {
        return (op.x == 0) && (op.y == 0) && (op.z == 0);
    }

    public void Show() => Console.WriteLine($"({x}, {y}, {z})");
}

class Program
{
    static void Main()
    {
        ThreeD a = new ThreeD(5, 6, 7);
        ThreeD b = new ThreeD(0, 0, 0);

        if (a) Console.WriteLine("a is true");   // ✅ a is true
        else   Console.WriteLine("a is false");

        if (b) Console.WriteLine("b is true");
        else   Console.WriteLine("b is false");  // ✅ b is false
    }
}

ما الفرق بين Method Overloading وOperator Overloading؟

✅
Method Overloading: تعريف أكثر من دالة بنفس الاسم لكن بـ signatures مختلفة (عدد أو نوع المعاملات).

Operator Overloading: إعادة تعريف سلوك رمز عملية حسابية (مثل + أو ==) ليعمل مع كلاس مُعرَّف من قِبل المستخدم بدلاً من الأنواع البدائية فقط.
٢

لماذا يجب أن يكون الـ operator دائماً public وstatic؟

✅
public: لأن العملية تُجرى من خارج الكلاس (مثلاً: c1 + c2) فيجب أن تكون مرئية للجميع.

static: لأن العملية تنتمي للكلاس وليس لكائن بعينه — المترجم يستدعيها تلقائياً بدون الحاجة لكائن.
٣

لماذا يجب تحميل == مع != معاً؟ ومثل ذلك true مع false؟

✅
لأن C# تفترض أن هذه العمليات متكاملة منطقياً — إذا عرّفت كيف يكون كائنَان متساويَين (==)، يجب أن تُعرّف أيضاً كيف يكونان غير متساويَين (!=). عدم تعريف الثاني يُسبب خطأ ترجمة.
٤

ما الفرق بين Unary وBinary وTernary operators؟

✅
Unary: يأخذ معاملاً واحداً — مثل ++x, -y, !flag
Binary: يأخذ معاملَين — مثل a + b, x == y
Ternary: يأخذ ثلاثة معاملات — الوحيد في C# هو ? : ولا يمكن تحميله.
٥

ماذا يحدث إذا حمّلنا الـ ++ وجعلنا return type هو void؟

🚫
خطأ ترجمة (Compile-time Error) — الـ return type للـ ++ و-- يجب أن يكون نفس نوع الكلاس حتى يتمكن المترجم من إسناد النتيجة مجدداً للكائن: obj = ++obj. الـ void يعني لا توجد قيمة تُرجَع فيتعذّر ذلك.

C# — Counter ++ Overloading 
using System;

class Counter
{
    public int number;

    public Counter() { }                      // Default Constructor
    public Counter(int v) { number = v; }       // Parameterized Constructor

    // تحميل الـ ++ operator
    public static Counter operator ++(Counter c)
    {
        Counter count = new Counter();
        count.number = c.number + 1;   // زيادة 1

}

class Program
{

        Console.WriteLine("After ++ : " + c1.number); // 6

        Console.WriteLine("After ++ : " + c1.number); // 7

}

using System;

مثال ٤ — تحميل الـ ~ (Toggle) — حل الواجب المنزلي

📋
الواجب: Overload the ~ operator to change an integer field value of a class from 0 to 1 and vice versa (Toggle). أي عند تطبيق ~ على الكائن، إذا كانت القيمة 0 تصبح 1، وإذا كانت 1 تصبح 0.
C# — ~ Toggle Operator HW Solution 
using System;

class Bit
{
    public int value;  // يجب أن يكون 0 أو 1 فقط

    public Bit(int v)
    {
        // تأكد أن القيمة 0 أو 1 فقط
        value = (v == 0) ? 0 : 1;
    }

    // تحميل الـ ~ operator — Toggle بين 0 و 1
    public static Bit operator ~(Bit b)
    {
        if (b.value == 0)
            return new Bit(1);  // 0 → 1
        else
            return new Bit(0);  // 1 → 0
    }

    public override string ToString() => value.ToString();
}

class Program
{
    static void Main()
    {
        Bit b1 = new Bit(0);
        Console.WriteLine("Before ~ : " + b1);   // 0

        b1 = ~b1;
        Console.WriteLine("After  ~ : " + b1);   // 1

        b1 = ~b1;
        Console.WriteLine("After  ~ : " + b1);   // 0

        Bit b2 = new Bit(1);
        Console.WriteLine("b2 Before ~: " + b2);  // 1
        b2 = ~b2;
        Console.WriteLine("b2 After  ~: " + b2);  // 0
    }
}
/* Output:
   Before ~ : 0
   After  ~ : 1
   After  ~ : 0
   b2 Before ~: 1
   b2 After  ~: 0  */

Binary Overloading — كلاس Fraction (كسور)

📋
أنشئ كلاس Fraction يمثل كسراً (بسط/مقام). حمِّل الـ + لجمع كسرَين حسب القاعدة الحسابية: (a/b)+(c/d) = (a*d + c*b)/(b*d).
C# — Solution Q4: Fraction Addition 
using System;

class Fraction
{
    public int Numerator, Denominator;  // البسط والمقام

    public Fraction(int n, int d)
    {
        Numerator   = n;
        Denominator = d != 0 ? d : throw new ArgumentException("Denominator cannot be 0");
    }

    // جمع كسرَين: a/b + c/d = (a*d + c*b) / (b*d)
    public static Fraction operator +(Fraction f1, Fraction f2)
    {
        int num = f1.Numerator * f2.Denominator + f2.Numerator * f1.Denominator;
        int den = f1.Denominator * f2.Denominator;
        return new Fraction(num, den);
    }

    // ضرب كسرَين: a/b * c/d = (a*c)/(b*d)
    public static Fraction operator *(Fraction f1, Fraction f2)
        => new Fraction(f1.Numerator * f2.Numerator, f1.Denominator * f2.Denominator);

    public override string ToString() => $"{Numerator}/{Denominator}";
}

class Program
{
    static void Main()
    {
        Fraction f1 = new Fraction(1, 2);   // 1/2
        Fraction f2 = new Fraction(1, 3);   // 1/3

        Console.WriteLine($"{f1} + {f2} = {f1 + f2}");   // 1/2 + 1/3 = 5/6
        Console.WriteLine($"{f1} * {f2} = {f1 * f2}");   // 1/2 * 1/3 = 1/6
    }
}
